# Review and QA, 2026-10-14

Seven reviewers (backend, shared libs, frontend data flow, laptop UI, phone UI, security, accessibility) and two QA explorers (a from-scratch run on an empty workspace through to invoicing, a regression run on the seeded week) reported 111 findings. Every blocker or major was checked by two independent verifiers (one reproducing on the running app, one reading the code); 32 were confirmed and none refuted. The fixes were built in six disjoint groups and re-checked: types tests 271 to 277, backend tests 96 to 107, type-check, lint and build clean.

## Confirmed and fixed

- **BE-1** (major, apps/backend/src/events/events.service.ts:116). EventsService.update (PATCH /admin/events/:id) reads the event, recomputes recipes and tasks (mergeLines, mergeTasks, shiftPrepDates on a date change) and writes them with a plain ddb.update, with no updatedAt condition. Every line and task endpoint goes through writeFields with the guard, but this path does not, so it can overwrite a line or task write that landed between its read and its write. The overwritten request got a 200.
  Fix: Route update() through the same guard as writeFields: pass {condition: "#ua = :expected", names: {"#ua":"updatedAt"}, values: {":expected": stored.updatedAt}} to ddb.update, use nextStamp(stored.updatedAt), and wrap the read-merge-write in withFreshEvent so it retries on ConditionalCheckFailedException.
- **BE-2** (major, apps/backend/src/events/events.service.ts:193). withFreshEvent retries a conditional-write failure only once, then returns 409 {code:"LINES_CHANGED"} and drops the write. With three or more writes in flight on the same event the third loses its retry too.
  Fix: Raise the retry budget (for example 4 attempts with a 20 to 50 ms jittered sleep between re-reads) in withFreshEvent; keep the 409 only after the last attempt. Optionally serialise writes per event on the frontend (queue in use-planning-data.patchLine/patchTask).
- **BE-3** (major, apps/backend/src/ingredients/ingredients.service.ts:337). importIngredients writes supplier: row.fournisseur for every matched ingredient, and the DTO (packages/types/src/dto/ingredients.ts:46) defaults fournisseur to "". The frontend (Ingredients.tsx:313) always sends fournisseur, empty when the CSV has no such column. A price-list CSV without a fournisseur column therefore blanks the supplier of every ingredient it matches. comment on the next line is handled correctly (row.commentaire || match.comment).
  Fix: supplier: row.fournisseur || match.supplier on line 337 (same pattern as comment), or make fournisseur optional in importIngredientRowSchema and only set it when present.
- **LIB-01** (major, packages/types/src/lib/reports.ts:245). incomeStatement reads CA with ledgerCaOfMonth for every month and ignores settings.ledgerStartYm, while apercu uses caOfMonth which falls back to yearActuals for months before the ledger start. For 2026, which REDESIGN.md line 1052 says has only December in the ledger, Résultats shows CA 0 for January to November, a negative résultat equal to the fixed charges, and an annual ISOC computed on a wrong cumulated result. The month rows carry no 'saisi' tag either.
  Fix: In incomeStatement, compute ca with caOfMonth(inputs, ym).amount ?? 0 and expose caSource on IncomeRow so Resultats.tsx can tag typed months; or, if typed months must stay out of Résultats, blank the row (ca undefined, no resultat, no impots) when !isLedgerMonth(settings, ym) and exclude it from the annual sum. Test: 'incomeStatement reads typed CA before ledgerStartYm' with the inputs above, expect months[0].ca toBe 5000 and annual.ca toBe 5000 (or the row to be blank and annual.ca toBe 0 if the second design is chosen).
- **LIB-02** (major, packages/types/src/lib/print.ts:257). perPersonPages builds candidates from input.people.filter(p => p.active) only. A row whose effective assignees are all inactive people is on nobody's page and is not in 'Sans personne' either (assignedTo is not empty), so it vanishes from the printed week. groupByPerson in planning.ts keeps such ids as extra groups, so the Day page shows the row and the print does not.
  Fix: Build candidates like groupByPerson: active people in settings order, then every id seen on a row that is not already listed (name from personName, which falls back to the id). Test: 'prints rows of an inactive person on their own page' with the inputs above, expect titles ['Ancien · semaine 42', 'Sans personne · semaine 42'] and the first page to carry line a.
- **DF-1** (major, apps/frontend/src/lib/api.ts:116). cached() stores the fetch result unconditionally when the promise resolves, even if invalidate() ran for that key while the request was in flight. use-planning-data.ts line 116 then does setEvents(ev) with that pre-write list, overwriting the local copy that replaceEvent had just updated. The stale list also sits in the api cache for 30 s, so the next page mounts (Day, Week, Events, EventDetail via api.events.list) read it without a network call.
  Fix: In cached(): only store the result if the entry is still ours: `.then((data) => { if (cache.get(key)?.promise === promise) cache.set(key, { data, ts: Date.now() }); return data; })` (invalidate() deletes the entry, so a write during the fetch leaves the cache empty).
